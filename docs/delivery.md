# API docs, Docker image and CI

## OpenAPI / Swagger UI

- **Swagger UI:** <http://localhost:8080/swagger-ui.html>
- **Spec:** `/v3/api-docs`, OpenAPI 3.1. CI also publishes it as the `openapi` artifact on every run.

Generated by springdoc-openapi from the controllers, so the docs can't drift from the code. On top of
the generated spec:

- **JWT bearer scheme**, so the **Authorize** button works: log in, paste the `accessToken`, and every
  "Try it out" call is authenticated. The token survives page reloads.
- **Public vs protected:** everything requires a token unless marked with an empty
  `@SecurityRequirements`: login, register, restaurant search/details and menus.
- **Real status codes:** `201` for creates (with `Location`), `204` for deletes, and `201`/`200` on
  `POST /orders` (new order vs idempotent replay).
- **Errors:** every operation lists `400` and `429`; protected ones add `401`/`403`; paths with an id add
  `404`. Business-rule errors are documented per endpoint with their codes (e.g. `409 CART_EMPTY,
  RESTAURANT_CLOSED...`). All of them use one shared `Problem` schema with
  `application/problem+json`, added by an `OpenApiCustomizer` instead of repeated on every method.
- **SSE endpoints** are documented as `text/event-stream` whose events carry an `OrderEvent`.

`OpenApiSpecTest` checks all of this and fails the build if, for example, an operation loses its summary
or a protected endpoint stops documenting `401`. Set `API_DOCS_ENABLED=false` to switch the docs off in
production.

## Docker image

Multi-stage `Dockerfile`:

1. **Build stage** (`eclipse-temurin:21-jdk`): first the Maven wrapper downloads Maven itself, then
   `pom.xml` is copied and dependencies are downloaded, then `src/` is copied and packaged. Each step is its
   own layer, so Maven is re-downloaded only when the wrapper version changes, dependencies only when
   `pom.xml` changes. A BuildKit cache mount keeps `~/.m2` between local builds without putting it in an
   image layer.

   Maven lives in `/opt/maven` (`MAVEN_USER_HOME`), not in `~/.m2`. **Found when a CI build failed:** the
   wrapper had put Maven in `~/.m2/wrapper`, inside the cache mount, and GitHub's layer cache doesn't keep
   cache mounts. So every CI image build downloaded Maven again, even when every other layer was cached,
   and one network hiccup doing so failed the build. Now it's an ordinary layer, which the cache keeps, and
   the download is retried up to 5 times. Checked by running the wrapper inside the build stage with
   networking turned off.
2. **Runtime stage** (`eclipse-temurin:21-jre`): only the JRE and the app, without the JDK, Maven or source.

| Practice | Why |
|---|---|
| Jar split into layers (`java -Djarmode=tools ... extract --layers --launcher`) | dependencies (53 MB) and application code (~0.9 MB) are separate image layers, so a code change pushes and pulls under 1 MB |
| Runs as a non-root `forkcast` user | a compromised app doesn't get root inside the container |
| `-XX:MaxRAMPercentage=75` | heap sized from the container's memory limit, not the host's |
| `-XX:+ExitOnOutOfMemoryError` | crash and get restarted rather than run on in a broken state |
| Exec-form `ENTRYPOINT` | `java` is PID 1 and receives `SIGTERM`, so `docker stop` triggers graceful shutdown |
| Tests not run in the image build | they need Docker (Testcontainers) and already ran in CI |

Measured: a cold build took 3 min 18 s; after a config change, rebuild + restart took 38 s. With a live
order stream open, `docker stop` took 1.5 s. The logs show the streams closing, then graceful shutdown
completing.

## Running everything in Docker

```bash
docker compose --profile app up -d --build
```

The `app` service sits behind a Compose **profile**, so plain `docker compose up -d` still starts only
MongoDB and Redis for running the app from an IDE. In the container the app reaches its dependencies
by service name (`mongodb`, `redis`): inside a container, `localhost` is the container itself. Compose waits for
MongoDB to be healthy before starting the app, and checks the app itself through
`/readyz`. Set `JWT_SECRET` in the environment or a `.env` file for anything beyond
local use.

## CI: GitHub Actions (`.github/workflows/ci.yml`)

On every push to `main`, every pull request, and on demand:

1. **Build and test** (on Ubuntu 22.04 for now; see below): a 5-second check that MongoDB can start on the
   runner, then JDK 21 with a cached Maven repository, then `./mvnw -B verify`. That runs all unit,
   web-slice and integration tests. The integration tests start real MongoDB (replica set) and Redis
   containers via Testcontainers on the runner's Docker engine. Test reports are uploaded if something
   fails, and the OpenAPI spec is uploaded every time.
2. **MongoDB on the newest runner** (doesn't block anything): the same MongoDB check on `ubuntu-latest`,
   to show when the tests can move back there.
3. **Docker image**, only if tests pass: built with Buildx, with layers cached in GitHub's Actions cache.
   On `main` it's pushed to GitHub Container Registry as `ghcr.io/asthaberi/forkcast:latest` and
   `:sha-<commit>`. Pull requests only check that the image builds.

Other details:

- **Least privilege:** the workflow token is read-only, and only the image job may write packages.
- **Concurrency:** a new push cancels the still-running pipeline for the same branch.

### What the first CI run caught

The first run on GitHub failed: 16 errors across the 4 test classes that start the full application
without their own Redis. Locally a development Redis was always running, so these tests had silently
depended on it, and the app itself couldn't start when Redis was down. Both are fixed; see
[order-tracking.md](order-tracking.md#startup-without-redis-a-bug-found-by-ci). This is why CI runs on a
clean machine: it catches what an always-on local environment hides.

### MongoDB stopped starting on GitHub's new runner image

On 21 October 2026, every integration test class failed on CI after ~60 s, while all 199 tests passed
locally. A re-run passed. Investigation:

1. **The failure:** Testcontainers' "Log output from the failed container" had MongoDB's own reason:
   `"id":12257600 … MongoDB cannot start: Linux kernel versions 6.19 and newer has a known incompatibility
   with this version of MongoDB` (SERVER-121912).
2. **Why it was intermittent:** the failed run was on runner image `20261018`, the passing re-run on
   `20261012`. The only relevant change between them was the **kernel: 6.17 → 7.0**. GitHub was rolling the
   new image out gradually, so each run was a coin toss.
3. **Not our code or the MongoDB image:** the `mongo:8.0` digest was the same in both runs, and locally.
4. **Reproduced locally:** a small preload library makes `uname()` report the runner's kernel
   (`7.0.0-1017-azure`). With it, MongoDB 8.0.34 fails with exactly the same fatal error; without it, it
   starts. Disabling the feature the check protects (`GLIBC_TUNABLES=glibc.pthread.rseq=0`) doesn't help: it's
   a plain version check, with no override.
5. **Upstream status:** reported to GitHub (actions/runner-images#15005). Their analysis: this kernel
   already contains the upstream fix, but MongoDB reads Ubuntu's version string instead of the upstream one
   (SERVER-131779). Fixed in MongoDB **8.0.35**, which isn't released yet. MongoDB 8.0.32 has the same check,
   so pinning an older patch isn't a way out either.

**What changed in CI:**

- The test job runs on **`ubuntu-22.04`** (kernel 6.8) until `mongo:8.0` has the fix. 22.04's deprecation
  brownouts only start in March 2027.
- **`check-mongo-starts.sh`** runs before the tests. If MongoDB can't start, the job fails in seconds with
  MongoDB's own message as an error annotation, not after 8 test classes × 60 s with the cause in the log.
- A **canary job** runs the same check on `ubuntu-latest` without blocking the build, so CI itself shows
  when it's safe to move back. It prints the runner's kernel, because during a rollout a green result on
  an old kernel proves nothing.
- The test container images are defined once (`TestContainers`), so moving to 8.0.35 is a one-line change.

Moving to MongoDB 9.0, which has the fix, was ruled out: a major-version upgrade isn't something to do
just to fix CI. The same check would also stop MongoDB 8.0.34 in `docker-compose.yml` on a Linux machine
with kernel 6.19+. Docker Desktop's kernel is 6.6, so it isn't affected.
