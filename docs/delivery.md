# API docs, Docker image and CI

## OpenAPI / Swagger UI

- **Swagger UI:** <http://localhost:8080/swagger-ui.html>
- **Spec:** `/v3/api-docs`, OpenAPI 3.1. CI also publishes it as the `openapi` artifact on every run.

Generated by springdoc-openapi from the controllers, so the docs can't drift from the code. On top of
the generated spec:

- **JWT bearer scheme**, so the **Authorize** button works: log in, paste the `accessToken`, and every
  "Try it out" call is authenticated. The token survives page reloads.
- **Public vs protected:** everything requires a token unless marked with an empty
  `@SecurityRequirements`: login, register, restaurant search/details and menus.
- **Real status codes:** `201` for creates (with `Location`), `204` for deletes, and `201`/`200` on
  `POST /orders` (new order vs idempotent replay).
- **Errors:** every operation lists `400` and `429`; protected ones add `401`/`403`; paths with an id add
  `404`. Business-rule errors are documented per endpoint with their codes (e.g. `409 CART_EMPTY,
  RESTAURANT_CLOSED...`). All of them use one shared `Problem` schema with
  `application/problem+json`, added by an `OpenApiCustomizer` instead of repeated on every method.
- **SSE endpoints** are documented as `text/event-stream` whose events carry an `OrderEvent`.

`OpenApiSpecTest` checks all of this and fails the build if, for example, an operation loses its summary
or a protected endpoint stops documenting `401`. Set `API_DOCS_ENABLED=false` to switch the docs off in
production.

## Docker image

Multi-stage `Dockerfile`:

1. **Build stage** (`eclipse-temurin:21-jdk`): copies `pom.xml` and the Maven wrapper first and
   downloads dependencies, then copies `src/` and packages. Dependencies are re-downloaded only when
   `pom.xml` changes, and a BuildKit cache mount keeps `~/.m2` between builds without putting it in an
   image layer.
2. **Runtime stage** (`eclipse-temurin:21-jre`): only the JRE and the app, without the JDK, Maven or source.

| Practice | Why |
|---|---|
| Jar split into layers (`java -Djarmode=tools ... extract --layers --launcher`) | dependencies (53 MB) and application code (~0.9 MB) are separate image layers, so a code change pushes and pulls under 1 MB |
| Runs as a non-root `forkcast` user | a compromised app doesn't get root inside the container |
| `-XX:MaxRAMPercentage=75` | heap sized from the container's memory limit, not the host's |
| `-XX:+ExitOnOutOfMemoryError` | crash and get restarted rather than run on in a broken state |
| Exec-form `ENTRYPOINT` | `java` is PID 1 and receives `SIGTERM`, so `docker stop` triggers graceful shutdown |
| Tests not run in the image build | they need Docker (Testcontainers) and already ran in CI |

Measured: a cold build took 3 min 18 s; after a config change, rebuild + restart took 38 s. With a live
order stream open, `docker stop` took 1.5 s. The logs show the streams closing, then graceful shutdown
completing.

## Running everything in Docker

```bash
docker compose --profile app up -d --build
```

The `app` service sits behind a Compose **profile**, so plain `docker compose up -d` still starts only
MongoDB and Redis for running the app from an IDE. In the container the app reaches its dependencies
by service name (`mongodb`, `redis`): inside a container, `localhost` is the container itself. Compose waits for
MongoDB to be healthy before starting the app, and checks the app itself through
`/actuator/health/readiness`. Set `JWT_SECRET` in the environment or a `.env` file for anything beyond
local use.

## CI: GitHub Actions (`.github/workflows/ci.yml`)

On every push to `main`, every pull request, and on demand:

1. **Build and test**: JDK 21 with a cached Maven repository, then `./mvnw -B verify`. That runs all unit,
   web-slice and integration tests. The integration tests start real MongoDB (replica set) and Redis
   containers via Testcontainers on the runner's Docker engine. Test reports are uploaded if something
   fails, and the OpenAPI spec is uploaded every time.
2. **Docker image**, only if tests pass: built with Buildx, with layers cached in GitHub's Actions cache.
   On `main` it's pushed to GitHub Container Registry as `ghcr.io/asthaberi/forkcast:latest` and
   `:sha-<commit>`. Pull requests only check that the image builds.

Other details:

- **Least privilege:** the workflow token is read-only, and only the image job may write packages.
- **Concurrency:** a new push cancels the still-running pipeline for the same branch.

Checked locally: the workflow file parses (SnakeYAML) and the exact test command passes (143 tests).
A real run happens once the repository is on GitHub.
